## 2. 已确认完成

### 2.1 总体架构

```text
Flutter App ← BLE → CH9141 ← UART3 → MSPM0G3507 MCU
Flutter App ← WiFi / RTSP → K230
K230 ← UART2 (PB15/PB16) → MCU
```

- App 负责蓝牙控制、PID 调参、RTSP 视频预览、MP4 录像和回放。
- K230 负责摄像头、钢珠检测、H.264 编码、RTSP；识别结果经 UART2 送 MCU。
- MCU 负责实时闭环，不直接进行图像处理。
- K230 到 MCU 的固定数据格式：

```text
$BALL,<x>,<y>\r\n
```

## 4. MCU 调试与接线

### 4.1 MCU 的 UART2（K230 数据口）

MCU 固件配置已确认：

```text
UART2，115200 8N1
MCU PB15 = UART2_TX
MCU PB16 = UART2_RX
```

K230 脚本当前默认厂商 FPIOA 映射：

```text
K230 GPIO11 = UART2_TXD
K230 GPIO12 = UART2_RXD
```

交叉连接：

```text
K230 GPIO11 / UART2_TX  ──> MCU PB16 / UART2_RX
K230 GPIO12 / UART2_RX  <── MCU PB15 / UART2_TX  （基线脚本仅发数据，回传可暂不接）
K230 GND                ─── MCU GND             （必须共地）
```

> 注意：先核对 K230 实际外接排针是否确实引出了 GPIO11/12。若板子实际接线用 GPIO5/6，只改 `k230_steel_ball_vendor_uart.py` 顶部的 `UART2_TX_PIN/RX_PIN`，不要改 MCU 的 PB15/PB16 配置。

### 4.2 MCU 的调试 UART1（printf 输出）

MCU 的 `printf` 固定重定向到 UART1，不会发到 K230 UART2 或 CH9141 蓝牙口：

```text
UART1，115200 8N1，无校验、无流控
MCU PA8 = UART1_TX
MCU PA9 = UART1_RX
```

USB-TTL 必须使用 **3.3V TTL 电平**，交叉接线：

```text
MCU PA8 / UART1_TX  ──> USB-TTL RX
MCU PA9 / UART1_RX  <── USB-TTL TX  （只看日志时可不接）
MCU GND             ─── USB-TTL GND
```

此前“串口无任何输出”已确认是接线错误。板载下载器或 USB 口**不等于 UART1 终端**；若未引出 PA8/PA9，插 USB 不会出现 `printf`。

MCU 的 `bsp_uart.c` 已将 `printf` 映射到 `UART1`。上电/复位后必须先看到：

```text
=== MSPM0G3507 SmartCar Template ===
BLE Init OK.
Ball Vision (K230) Init OK.
Init OK.
OLED Init OK.
```

若这些启动信息都没有：先处理 UART1/USB-TTL 接线、终端 COM 口、115200 设置或重新烧录，而不是排查 K230 模型。

### 4.3 MCU 新增的 K230 接收诊断

已修改：

```text
E:\Supercar\MCU\empty.c
```

默认开启：

```c
#define BALL_VISION_DEBUG_PRINT 1
```

主循环每秒经 UART1 输出一次，且 UART2 中断内不打印，因此不影响串口接收实时性。

未收到完整有效帧：

```text
K230 BALL: waiting frames=0 err=0
```

已收到数据：

```text
K230 BALL: x=158 y=203 age=25ms frames=47 err=0
```

判定：

- `frames` 持续增长：K230→MCU 协议和接线正常；
- `age` 通常应低于约 100 ms：K230正在持续上报；
- `err=0`：UART2 未发生硬件接收错误；
- `waiting frames=0 err=0`：MCU本身正常，但尚未收到格式正确的 `$BALL,x,y\r\n`；优先检查 K230程序是否运行、UART引脚和共地。

调试结束可把 `BALL_VISION_DEBUG_PRINT` 改为 `0` 关闭。

## 6. 下一步执行顺序

1. **烧录最新 MCU 固件**，接好 USB-TTL 的 PA8→RX、GND→GND，115200 打开终端并复位；确认五行 MCU 启动日志出现。
2. 上传厂商 YOLO11n 模型、标签和 `k230_steel_ball_vendor_uart.py` 到 K230 指定路径。
3. 只运行 K230 基线脚本，观察屏幕框和 K230 终端 2 秒统计；不要运行 RTSP 脚本。
4. 接好 K230 GPIO11→MCU PB16 与两端 GND，观察 MCU UART1：从 `waiting` 变为 `x=... y=... frames=...`。
5. 让钢球静止、缓慢移动、移出画面，记录 K230 和 MCU 各 10–20 秒日志，判断检出率、误检、坐标抖动和丢帧。
6. 只有厂商模型与 UART 稳定后，再新建“YOLO11n + H.264 RTSP + UART2”双通道脚本。融合时保留：
   - chn0：800×400 YUV420SP → VENC → H.264 RTSP；
   - chn1：AI 输入；
   - UART 协议不变；
   - 不能同时运行独立 RTSP 脚本和独立 YOLO 脚本。
7. 最后才进入摆杆角度 PID、球位置 PID 与小车加速度前馈闭环开发。

## 7. 已知风险与禁止事项

- **不要再用旧 gz 模型直接闭环**：当前真球检测置信度低，低阈值有背景误检。
- **不要再尝试 gz 的 1088×720 AI 输入**：此前该路径在当前板上不稳定，出现过 IDE interrupt；800×400 为已验证稳定配置。
- **不要把厂商 PipeLine 脚本与现有 RTSP 脚本同时执行**：它们都会占用相机/媒体资源。
- 厂商基线输出是 **320×320 像素坐标**；MCU 解析器接受该范围，但后续控制标定必须把像素坐标映射到摆杆物理位置（mm）。
- K230 GPIO11/12 只是厂商示例映射，务必以实际板卡排针和接线为准；电平为 3.3V TTL，必须共地。
- 不要在 UART2 RX 中断内做 `printf`、浮点计算或控制算法；当前架构只在中断内解析并在主循环读取快照，是正确实时性边界。
